Merge the Bungee and Velocity proxy modules into a single jar

FMessageBungee and FMessageVelocity were parallel ports of the same
logic against two proxy APIs: 18 identically named classes, ~88% of
which were pure duplication, the rest being type substitutions
(ProxiedPlayer/Player, String/TextComponent, null/Optional). Every
functional change had to be written, reviewed and fixed twice.

Both modules are replaced by FMessageProxy, which produces one jar
loading on either proxy. Three properties make that possible:

  - plugin.yml (BungeeCord) and velocity-plugin.json (Velocity, generated
    by the velocity-api annotation processor) coexist in the same jar;
  - class loading is lazy and no shared class references either entry
    point, so neither bootstrap is ever loaded on the other platform;
  - acf-bungee and acf-velocity share 125 acf-core classes with identical
    bytecode, so the shade plugin merges them into a single relocated
    copy while keeping both platform managers.

The module is split into platform/ (abstraction contract), core/ (all
the logic, written against it), and bungee/ + velocity/ (thin adapters).
Duplicated logic goes from ~2250 lines to zero; the 1356 lines of the
core are written once.

The core now produces legacy § text and lets each adapter convert it at
the last moment, rather than manipulating platform components. This is
what keeps Adventure out of the core and out of the jar: BungeeCord does
not ship it, and a shaded copy handed to Velocity would throw a
ClassCastException.

Fixed along the way:

  - MessageManager was built before the command manager in both modules
    and captured a null reference, throwing as soon as a message hit an
    ignore or a msgtoggle;
  - Velocity's MessageListener passed an Optional<Player> instead of the
    player to getCommandIssuer, breaking group messages;
  - {#rrggbb} hex colours worked on BungeeCord only and were silently
    dropped on Velocity; both now share the same formatter;
  - session state (reply target, spies, msgtoggle) used ArrayList and
    HashMap while being written from proxy network threads;
  - removed the dead playerStaff field and the unreferenced
    @bungeeplayers completion.

Test suite added, 177 tests where there were none. Two of them carry the
architecture:

  - ChatProtocolTest pins the binary frame format shared with
    FMessageBukkit down to the byte. FMessageBukkit is not rebuilt with
    the proxy, so that format is a frozen contract and a silent break
    would only show up in production.
  - ArchitectureTest (ArchUnit) forbids any platform import from core/ or
    platform/. Both proxy APIs are on the compile classpath, so a stray
    import compiles, passes every other test, and only fails at startup
    on the other proxy.

Build: Java release 21 across all modules (was source/target 16),
surefire and failsafe added, annotationProcessorPaths declared
explicitly since JDK 23 no longer runs processors found through the
classpath alone — without it velocity-plugin.json is not generated, the
build stays green and the jar is invisible on Velocity.

BREAKING: the proxy jar is renamed FMessage-Proxy-x.x.x.jar. Existing
installations must delete FMessageBungee-x.x.x.jar or
FMessageVelocity-x.x.x.jar first, otherwise the plugin loads twice. The
BungeeCord plugin name and the Velocity plugin id are deliberately
unchanged, so data folders, configuration, languages and database carry
over untouched.
